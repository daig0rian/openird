# clean-room 作業手順

OpenIRD の配布物は GPL ソースからの再ビルドと自前実装だけで構成する。ベンダ
バイナリは解析対象であって配布素材ではない。著作権上の安全は、次の順序規律と
その証跡（コミット trailer）で担保する。

## 順序は固定: 観察 → 仕様化 → 実装

1. **観察** — 走らせて外から見える挙動を採る。`strings` / usage / ログ / `/proc`
   / バス信号 / USB 列挙。これは「事実・構造・語彙」の抽出であり、制御フロー
   （アルゴリズム＝著作権が守る表現）には踏み込まない。
2. **仕様化** — 観察結果を `docs/specs/` に**文章の仕様**として起こす。ここが
   観察と実装を隔てるファイアウォール。仕様に書けるのは外から見える事実・構造・
   語彙だけで、**逆アセ由来の内部ロジック・具体アドレス・コード由来の数式は
   OpenIRD では扱わない**（仕様にも書かないし、置き場所も設けない）。
3. **実装** — **仕様だけ**を見て自前コードを書く。ベンダの逆アセを横に置いて
   書かない。理想は観察者 ≠ 実装者。単独なら時間で分ける。

## コミットでの宣言（監査線）

| provenance | trailer | Spec-Ref |
|---|---|---|
| 自前コード（仕様のみ根拠） | `Origin: clean-room` | **必須** |
| GPL 上流の派生・パッチ | `Origin: gpl-derived` | 任意 |
| 観察由来の仕様・記録 | `Origin: observed` | — |
| 無改変の上流取り込み | `Origin: upstream` | — |

`Spec-Ref: docs/specs/spec_bmmpx1301.md#6.8` のように、実装が根拠とした仕様節を
必ず引く。これが「逆アセを見て書いていない」ことの外形的証跡になる。

## 禁止（例外なし）

- ベンダバイナリ・ダンプ・ファーム・鍵の commit（`.gitignore` + pre-commit で拒否）。
- 限定受信の復号ロジック・鍵・回避手順（スコープ外。CONTRIBUTING.md §0）。
- 鍵抽出ロジック・ツールの commit（機構は問わない）。値そのものと違い blob 検査
  では拾えないため、レビュー時に PR の目的で判断する（CONTRIBUTING.md §0）。
  ハードウェア動作ファームの cutter は別扱い＝範囲内（`docs/architecture.md`）。
- 公開しない作業メモ（`CLAUDE.md` 等）の commit。
