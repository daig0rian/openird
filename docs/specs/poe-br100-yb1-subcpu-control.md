裏 CPU（AV サブシステム）向けの**自前ファームを開発するときに使える、メイン CPU 側の口**を
まとめる。これまでの理解は「FW を DRAM に置く（§5）」と「共有メモリのコマンドスタック＋
合図（受信スタック仕様 §72）」の 2 つだけだったが、**BHIF には CPU ごとの制御ブロックがあり、
裏 CPU のリセット・起動ベクタ・アドレス窓・割り込みの振り分け・NMI がメイン CPU から
見えている**。さらに、**電源を切らずに AV サブシステムをやり直せる**（§5.2）。

## 0. スコープ

- 対象: メイン CPU と裏 CPU（MIPS32 4KEc）の間の、ハードウェア上のインターフェース。
- **限定受信（B-CAS / MULTI2 / ARIB スクランブル解除）は永久に対象外。** 公開資料上、
  EMMA3SE/P には「Security CPU」がある（§1）。§3.3 の 3 つめの制御ブロックがそれである
  可能性があるので、**正体が分かるまで書き込まない**。
- 裏 CPU の**ベンダ FW を配布しない**方針（CLAUDE.md §1-1）は変わらない。本書は自前 FW を
  載せるための口を扱う。

## 1. プロセッサ構成（公開資料）

Renesas の EMMA3SE/P フライヤ（2011.08・µPD6142xF1）より【公開】:

- **Main CPU と Sub CPU はどちらも MIPS32 4KEc**（合計 1224 DMIPS）。構成は
  「RTOS-RTOS」か「Linux-RTOS」で、**sub CPU の RTOS が音声・映像などの実時間処理**を担う。
- **Security CPU**（EMMA3SE/P のみ・CA ベンダ向け）と **Audio DSP** が別にある。
- Stream processor: **2 × シリアル入力または 1 × パラレル**、**108 PID フィルタ（うち 3 つが
  PCR 用）**、96 セクションフィルタ。DVB-T1/C1 の復調器を内蔵（任意）。
- 周辺: 2 × FUART、2 × I²C、2 × スマートカード、IR 受信、**GIO バス**。
- 資料番号: データシート R19DS0018EG0100、ユーザーズマニュアル R19UH0051EG0107、
  リファレンスデザイン R19PF0036ED0000。**いずれも一般公開されていない**（受信スタック
  仕様 §9.4 と同じ結論）。

照合:

- 「108 PID フィルタ」は、受信スタック仕様 §73.4 で実測した PID 表の項数（`0x00`〜`0x6b`
  の 108 個）と一致する。
- 裏 CPU が 4K 系であることは csd の起動メッセージ `4KE POWER-ON` と合う（§5）。
- 裏 CPU FW の `strings` の先頭に `RX4000V4 Copyright (C) RENESAS ELECTRONICS 2000-2011`。
  **Renesas の μITRON 4.0 系 RTOS（RX4000）**で動いている。キュー・セマフォの名前
  （`evtNotifyQue` `demuxSemphore` `taskRecvQue` など）は残っているが、**printf の書式や
  ログの文字列は 1 本も無い**＝ベンダ FW にはデバッグ出力が無い。

## 2. BHIF の CPU 制御ブロック（全体）

BHIF（`0x10000000`〜）には、**同じ並びのレジスタ組が CPU ごとに 1 組ずつ、3 組ある**。
メイン CPU の組を基準に、裏 CPU の組は **`+0xd0`**、3 つめの組は **`+0x1d0`** ずれている。

このずれは推測ではなく、**GPL が両側に名前を付けている 5 組がすべて `+0xd0` で揃う**
ことから言える:

| メイン CPU（名前の出典） | 裏 CPU（名前の出典） | 差 |
|---|---|---|
| `INT_ST_0` `+0x030`（kernel・U-Boot） | `SUB_INT_ST_0` `+0x100`（kernel） | `+0xd0` |
| `INT_EN_0` `+0x040`（kernel・U-Boot） | `SUB_INT_EN_0` `+0x110`（kernel） | `+0xd0` |
| `MAIN_PADR_EN` `+0x070`（U-Boot） | `SUB_PADR_EN` `+0x140`（U-Boot） | `+0xd0` |
| `MAIN_PADR1_BASE` `+0x080`（U-Boot） | `SUB_PADR1_BASE` `+0x150`（U-Boot） | `+0xd0` |
| `MAIN_PADR2_BASE` `+0x090`（U-Boot） | `SUB_PADR2_BASE` `+0x160`（U-Boot） | `+0xd0` |

kernel の `include/asm-mips/emma/emmaxxx.h` には `CONFIG_EMMA_SUBCPU` という切り替えがあり、
立てると `EMMA_BHIF_INT_ST_*`／`INT_EN_*` が `SUB_INT_ST_*`／`SUB_INT_EN_*` に差し替わる
（`arch/mips/emma/Kconfig` では EMMA3P/EMMA3PF で CPU_MIPS32_R2 のとき既定で有効）【GPL】。
∴ **同じ kernel ソースを「裏 CPU 側」でビルドする前提の設計**で、裏 CPU から見た割り込み
コントローラはこのブロックそのものである。

- `ALTERNATE1` は kernel が `+0x018`、U-Boot が `+0x02c` と、**出典で番地が食い違う**。
  本書では使わない。

### 3.2 裏 CPU の組（`+0xd0`）

| オフセット | 名前（出典） | 実測値 | 読み |
|---|---|---|---|
| `+0x100`〜`+0x108` | `SUB_INT_ST_0..2`（kernel） | `0` / `00000200` / `80000000` | メイン CPU の `INT_ST` と同じ値＝**同じ割り込み源の別の見え方** |
| `+0x110`〜`+0x118` | `SUB_INT_EN_0..2`（kernel） | `00000080` / `0` / `00000eee` | §6 |
| `+0x120`〜`+0x128` | 【推定】`SUB_INT1_EN_0..2` | 全部 `0` | 2 本目の割り込み出力 |
| `+0x130` | 【推定】`SUB_NMI_ST` | `00000001` | メイン CPU（`+0x060`）と同じ値 |
| `+0x134` | 【推定】`SUB_NMI_EN` | `0` | §8 |
| `+0x140` | `SUB_PADR_EN`（U-Boot） | `00000001` | §4 |
| `+0x144` | `SUB_PADR0_MASK`（U-Boot） | `0003fffe` | §4 |
| `+0x148` | `SUB_PADR0_TARGET`（U-Boot） | `00000002` | §4 |
| `+0x150`〜`+0x168` | `SUB_PADR1/2_{BASE,MASK,TARGET}`（U-Boot） | 全部 `0` | 未使用の窓 |
| **`+0x180`** | **【実測】裏 CPU のリセット**（名前は並びから `SUB_RESET`） | 電源投入直後 **`3`**／csd の後 **`0`** | `3`＝止まっている。解除は csd（§5.1）。**メイン CPU から `3` を書いても残らない**（§5.3） |
| `+0x184` | 【推定】`SUB_CTRL` | `00000001`（観察した全状態で同じ） | メイン CPU の `MAIN_CTRL` と同じ値 |
| **`+0x190`** | **【実測】裏 CPU の起動ベクタの基底**（名前は並びから `EXCEPT_VECT_BASE_ADDRESS`） | 電源投入直後は起動ごとに違う値（例 `187f7800`）／csd の後 **`80030000`** | **裏 CPU FW のロード番地 `0x30000`（§5）の KSEG0 表記そのもの**。書くのは csd（§5.1） |
| `+0x194` | 【推定】裏 CPU の `OFFSET_ADDRESS` | `0` | |

- `+0x140`〜`+0x148` の実測値は、U-Boot の `lowlevel_init.S` が書く値（§4）と完全に一致する
  ＝U-Boot の名前はこの機種の実機に当てはまる。
- `+0x180`/`+0x190` を書くコードは GPL の U-Boot にも kernel にも無く、**csd の load（`NORMAL`）の
  前後で値が変わる**ことを実測した（§5.1）。

### 3.3 3 つめの組（`+0x1d0`）

| オフセット | 並びから当てた名前【推定】 | 実測値 |
|---|---|---|
| `+0x200`〜`+0x208` | `INT_ST_0..2` | `0` / `00000200` / `80000000`（他の 2 組と同じ） |
| `+0x210`〜`+0x228` | `INT0_EN`／`INT1_EN` | 全部 `0` |
| `+0x230` | `NMI_ST` | `00000001` |
| `+0x240`〜`+0x268` | `PADR_EN`／`PADR*` | 全部 `0` |
| **`+0x280`** | **`RESET`** | **`00000003`**（他の 2 組は `0`） |
| `+0x284` | `CTRL` | `00000001` |
| `+0x290` | `EXCEPT_VECT_BASE_ADDRESS` | 起動ごとに違う（`099fe000` / `099de000`）＝電源投入時の値のまま |

- **RESET の `3` は、裏 CPU が csd に解除される前と同じ値**（§5.1）＝電源投入時の「止まっている」
  状態のまま、**誰にも起こされていない 3 つめのプロセッサ**に見える【推定】。ベクタも設定されて
  いない（起動ごとに違う値）し、割り込みも 1 本も許可されていない。
- 公開資料（§1）にある 4KEc 以外のプロセッサは **Security CPU** と **Audio DSP**。
  どちらかは分からない。**Security CPU なら限定受信の領分なので、本プロジェクトでは
  触らない**（§0）。YB1 は音声出力を持たないので、Audio DSP が止まっているのも辻褄は合う。
- 受信スタック仕様 §73.5 で「Initialise（`nr=0x01`）の瞬間に動く BHIF の語」として挙げた
  `+0x060` `+0x130` `+0x230` は、**3 組の NMI_ST** だった（意味は未確定）。

## 4. 裏 CPU のアドレス窓（`SUB_PADR`）

U-Boot の `board/renesas/emma3sep/lowlevel_init.S` は、DRAM の初期化の直後に
「Memory Window setting for Sub CPU」として次を書く【GPL】:

```
HIF_SCPU_PADR0_MASK   = 0x0003FFFE
HIF_SCPU_PADR0_TARGET = 0x00000002   /* 0x00002000 -> 0x00000000, 8KB */
HIF_SCPU_PADR1_*      = 0            （使わない）
HIF_SCPU_PADR2_*      = 0            （使わない）
HIF_SCPU_PADR_EN_WIN  = 0x00000001   /* Win0 */
```

- 実機の値（§3.2）と一致する【実測】。
- 窓は 3 つ。**窓 0 には BASE が無く**（基点が固定）、窓 1・2 は BASE/MASK/TARGET を持つ。
  `SUB_PADR_EN` のビットは窓 0＝bit 0、窓 1＝bit 8、窓 2＝bit 16（U-Boot の判定の仕方から）【GPL】。
- MASK と TARGET を 4KB 単位とみなすと、窓 0 は **8KB を物理 `0x2000` に向けている**
  【推定】。コメントの「8KB」と合う。裏 CPU の低位番地が、メイン CPU の例外ベクタのある
  物理 `0x0000`〜`0x0fff` を潰さないよう、別の場所へ逃がしている形に見える。
- メイン CPU 側にも同じ形の窓（`MAIN_PADR*`）があるが、使われていない（全部 0）。

**自前 FW への含意**: 裏 CPU から見た番地を、窓 1・2 で DRAM の任意の場所に付け替えられる
（決め打ちの番地でリンクした FW を、メイン CPU の都合のよい場所に置ける）【推定・未検証】。

## 5. 起動とリセット

**FW の置き方**（ベンダの `setup.sh` と `fw_load.sh`・平文）:

```
mount -t squashfs /dev/mtdblock5 /tmp/emma_fw
dd if=emma3sep_driver_std_op0.mem of=/dev/mem seek=$((0x30000/1024)) bs=1024
```

ヘッダ・署名・復号は無い。**この番地 `0x30000` が、裏 CPU の組の `+0x190`（`80030000`）と
一致する**（§3.2）。

**`csd.ko` が持っている起動の手段**（`nm`・`strings`・`objdump -h` のみ）:

| 種類 | 観察できたもの |
|---|---|
| シンボル | **`Reset_SubCPU`（global `T`・`EXPORT_SYMBOL` は無い）**、`Request_SpecialCmdExecute`（export）、`read_sw_int_special`、`init_csd` |
| 起動時の文字列 | `Execute: USR_INIT_CODE`、**`4KE POWER-ON`**、`Special Command Timeout` |
| module_param | `CSD_MODE`（charp）。文字列として **`NORMAL` / `FORCE` / `NOINIT`** を持つ。実機の値は `NORMAL` |
| 割り込み | `CSD_SPECIAL`（SW int 1）は起動時に 1 回だけ鳴る（実測で 1 回・受信スタック仕様 §12.3） |

- ∴ **裏 CPU の電源投入（リセット解除）と初期化コードの実行は、メイン CPU 側の csd が
  行っている**（§5.1 で実測）。
- `Reset_SubCPU` は kallsyms に載っている（`CONFIG_KALLSYMS=y`）ので、`tools/yb1-mmac` の
  やり方で名前で呼べる。**ただし呼ぶのはベンダのコードを実行することで、段階 B の道具
  扱い**（本書では呼んでいない）。

### 5.1 csd の load で変わるもの（実測・2026-09-27）

段階 C リグのフックに一度きりのフラグ `openird-nocsd-once` を足し、**csd と val_merge を
load しないで起動**した（FW の `dd` は行う）。その状態を撮ってから `insmod csd.ko` した。
書き込みは csd 自身のものだけで、我々は読んだだけ。

| `CSD_MODE` | 割り込みの登録 | 裏 CPU の起動 | BHIF の変化 |
|---|---|---|---|
| `NOINIT` | しない | しない | **0 語** |
| `FORCE` | する（`init_irq`） | **しない**（`USR_INIT_CODE` も `4KE POWER-ON` も出ない・`CSD_SPECIAL` は増えない） | `SW_INT_EN` だけ |
| `NORMAL` | する | する（`Execute: USR_INIT_CODE` → `4KE POWER-ON`、`CSD_SPECIAL` が 1 増える） | 下表 |

電源投入直後（csd 無し）→ `NORMAL` の load 直後で変わった BHIF の語は**これで全部**:

| 番地 | 前 | 後 | 読み |
|---|---|---|---|
| `+0x110` `SUB_INT_EN_0` | `0` | `00000080` | 合図（源 7）を裏 CPU に通す |
| **`+0x180`** | **`3`** | **`0`** | **リセット解除** |
| **`+0x190`** | ゴミ（`187f7800`） | **`80030000`** | 起動ベクタ＝FW の番地 |
| `+0x1a4` `SW_INT_EN` | `0` | `ffffff07` | メイン CPU 側の SW 割り込みを受ける |
| `+0x1ac` | ゴミ | `a0010000` | 共有メモリの先頭 |
| `+0x1b4` | `0` | `00070000` | 合図のマスク |

- BHIF 以外では、**物理 `0x2000` の 8KB（§4 の窓 0 の先）**と共有メモリ（`0x10000`〜）の中身が
  変わった（ハッシュの比較のみ。中身は見ていない）。2 回目以降の `NORMAL` の load では、この
  8KB は変わらなかった。
  - **8KB の中身は FW のイメージの写し**（受信スタック仕様 §79.1・位置だけで照合）: 0 でないのは 6 語
    （`+0x000`〜`+0x008`・`+0x180`〜`+0x188`）だけで、FW ファイルの `0x210`〜・`0x390`〜 の語と
    一致する。csd.ko など他のファイルには無い。（本節の旧版にあった「`USR_INIT_CODE` を置いて
    いる」という見立ては、これで否定された。）
- **上表の 6 語は、全部を csd がその時に書くのではない**（受信スタック仕様 §79.2・20µs ごとの
  見張り）。csd の `insmod` の最中に変わるのは `+0x1a4`（割り込みの登録）と、**`+0x190`・`+0x180`
  （`3` → `0`、1 回は `3` → `2` → `0` の 2 段）だけ**。約 81 ms 後（`insmod` が返った後）に
  クロック／リセットの 1 語（§5.5）・8KB の 6 語・共有メモリの 0 埋めが起き、裏 CPU の合図
  （`SW_INT` bit 1）の直後に `+0x1ac`・`+0x110`・`+0x1b4` が書かれる。後半を起動した FW 自身が
  しているか csd の遅延処理かは未判別（FW 自身とみるのが自然【推定】）。
- `SUB_INT_EN_2 = 00000eee` は csd ではなく、**`val_demux nr=0x01`（Initialise）の後に**現れる
  ＝裏 CPU の FW が自分で AV の割り込みを許可している。同じときに 3 組の `NMI_ST`
  （`+0x060` `+0x130` `+0x230`）が `0` → `1` になり、`+0x314`〜`+0x320` も書かれる。

### 5.2 ★ 電源を切らずに AV サブシステムをやり直す（実測・2 回成立）

段階 C の走行のあとで次を行うと、**`val_demux nr=0x01`（Initialise）が再び `0` を返し、
ハンドルが電源投入直後と同じ値になり、PES が出る**。MXL683 の選局はそのまま残るので、
やり直すのはデマルチプレクサ側だけでよい。

```
rmmod val_merge
rmmod csd
dd if=<mtd5>/emma3sep_driver_std_op0.mem of=/dev/mem bs=1024 seek=192   # 物理 0x30000
insmod csd.ko            （CSD_MODE=NORMAL。4KE POWER-ON が出て CSD_SPECIAL が 1 増える）
insmod val_merge.ko
```

実装は `tools/vendor-rootfs/av-restart.sh`（`/app/setting` に置いて `sh` で実行）。

| 走行 | その前にしたこと | `nr=0x01` | ハンドル 9 個 | 出たもの |
|---|---|---|---|---|
| 1 | 電源投入 → csd `NORMAL`（§5.1） | `0` | 既知の値（`0x00010000` `0x02010002` …） | ペイロードフィルタに映像 PID `0x0100` → FIFO にスクランブルされたまま入る（PES は出ない＝頭が読めない） |
| 対照 | 何もせずにもう一度 Initialise | **`-1`** | — | — |
| 2 | `rmmod` ×2 → `dd` → csd `FORCE` → `rmmod csd` → csd `NORMAL` → val_merge | **`0`** | **1 と同一** | 字幕 PID `0x0130`・新しいリング `0x0e000000` に **PES（`00 00 01 bd`）**。FIFO から 1 の `0x0100` が消え、新しい設定だけになった |
| 3 | `av-restart.sh`（`rmmod` ×2 → `dd` → csd `NORMAL` → val_merge） | **`0`** | **1 と同一** | 字幕 PID・リング `0x0d000000` に新しい PES（PTS が 2 より後） |

どの走行も、失敗は電源投入直後と同じ既知の 3 本（`nr=0x0a`/`0x47`/`0x67` の `-3`・
受信スタック仕様 §34.3）だけだった。**∴ 受信スタック仕様 §31.3 の「1 試行 = 1 電源入れ直し」は、
csd の入れ直しで置き換えられる。**

- **`dd` が要るかは未確認**（2・3 とも `dd` してから入れた）。
- `CSD_MODE=FORCE` は起動をやり直さないので、この用途には使えない（2 で確認）。

### 5.3 メイン CPU からは、リセットをかけ直せなかった

- **`rmmod csd` では裏 CPU は止まらない**。`+0x180` は `0` のまま、FIFO にも映像が入り続け、
  SRAM も動き続ける。
- **`+0x180` に `3` を書いても残らない**（`yb1-poke` で書いて読み返すと `0`。ユーザの許可のもと
  1 回だけ実施）。書いた後も共有メモリ・`0x2000` の 8KB・`SW_INT` は 1 語も変わらず、再起動の
  形跡（`CSD_SPECIAL` に当たる合図）も無かった。∴ **`+0x180` は電源投入時に `3` で始まり、
  メイン CPU からは解除しかできない**（書き込みに保護があるか、止め直しは別のレジスタ）。
- クロック／リセットのページの `0x10111058` bit 3 も落とせなかったが、裏 CPU の起動との関係は
  確認できていない（§5.5）。
- ∴ §5.2 の「やり直し」は、**止めて起こす（ハードのリセット）ではなく、走っている FW に
  初期化をやり直させている**とみるのが自然【推定】。自前 FW にとっての含意は §5.6。

### 5.4 裏 CPU が止まっている間も動く SRAM の語（実測）

csd を load する前（`+0x180 = 3`）に AV データ SRAM（`0x10030000`〜）を 1 秒あけて比べると、
**27 語が動いていた**:

| 番地 | 中身の見立て |
|---|---|
| `0x1003e964` / `e96c` | 時刻 |
| `0x1003ec54` / `ecd4` / `ed54` | **FIFO 0/1/2 の制御ブロックの `+0x54`（時刻・受信スタック仕様 §73.6）** |
| `0x1003fe34`〜`fe6c`、`0x1003fee4`〜`fef4`、`0x1003ff34`〜`ff6c`、`0x1003ffe4`〜`fff4` | 時刻と計数の組（受信スタック仕様 §73.5 の「信号が無くても動く」組） |

- 裏 CPU が止まっているなら、これらを書いているのは**ハード**である。受信スタック仕様 §73.3/§73.6
  で「FW の変数か、ハードが読み書きする記述子か区別できない」としていた SRAM に、
  **ハードが直接書く語がある**ことが分かった。
- 刻みは、FIFO 制御ブロックの `+0x54` が **FW の初期化前は 1 秒で約 4,630 万、FW 稼働中は
  27,004,536（3 秒で 81,004,898）＝27.000 MHz**（後者は受信スタック仕様 §73.6 と一致）。
  `0x1003ffec` は初期化前から約 2,714 万/秒。∴ **FIFO の時刻はハードの計数器で、その刻みを
  FW が初期化で 27 MHz に合わせている**とみられる【推定】（初期化前の値は 1 回の測定）。
- csd の `NORMAL` の load 直後（裏 CPU は走っているが Initialise 前）も、動く語は 27 のまま。
  Initialise の後に映像を取り込んでいる間は、約 490〜500 語に増える（同じ比べ方・1 秒）。

### 5.5 クロック／リセットのページ（`0x10111000`〜・実測・2026-09-27）

U-Boot の `CLK_BASE = 0x10111200`（`CHIF_PERICLK_SEL` が `+0x1b4`）を含む 4KB のページを、
`range` モード（番地を出してから 1 語読む）で 3 状態読んだ。**全 1,024 語が固まらずに読める。**
中身があるのは約 30 語（付録 C）。

| 状態 | 比べた結果 |
|---|---|
| 電源投入直後（telnet が上がった直後に読んだ・csd 無し・`+0x180 = 3`）→ 数十秒後に csd `NORMAL` を load し、その約 2 秒後 | 4 語が違った（下表） |
| csd の load の後 → Initialise と走行の後 | 変化なし |

| 番地 | 前 | 後 | 裏 CPU の起動で変わるか |
|---|---|---|---|
| `0x10111030` | `0` | `00000004` | **変わらない**（下の訂正） |
| `0x10111034` | `0` | `00000004` | **変わらない** |
| `0x10111058` | `00000003` | `0000000b`（bit 3 が立つ） | **変わらない** |
| **`0x101113b0`** | `0a220000` | **`00020000`**（bit 21・25・27 が落ちる） | **変わる**（裏 CPU の解除の約 81 ms 後・受信スタック仕様 §79.2） |

**訂正（2026-09-28）**: 本節の旧版は、4 語とも csd の load で変わるとして「csd が起こすときに
書くのは計 10 語」と書いたが、**誤り**だった。

- 受信スタック仕様 §79.2 の見張り（20µs ごと）では、`0x10111030`/`034`/`058` は csd の load の
  20 秒後も `val_merge` の load の後も `0`/`0`/`3` のままだった。
- この取り直しとして、csd 抜きで起動したあと csd と `val_merge` を入れた状態（起動後約 10 分）を
  読んでも `0`/`0`/`3` だった（`0x101113b0` だけ `00020000`）。
- 旧版の「前」は telnet が上がった直後で、`setup.sh` の後半が走っていた可能性がある。
  「後」はそこから数十秒〜1 分ほど後。**3 語を変えたのは csd 以外の何か**で、何かは未確認。
  その前の起動（選局と走行を重ねた後）でも `4`/`4`/`b` だった。
- ∴ **裏 CPU の起動に伴ってこのページで変わるのは `0x101113b0` の 1 語だけ**。

**書き込みの試験**（ユーザの許可のもと・書いたのは電源投入時の値だけ）。裏 CPU が走り、
映像を FIFO に取り込んでいる状態で 1 語ずつ書き、生存（読み取り専用の要求 `val_demux nr=0x07`
→ 裏 CPU のコマンド `0x1906` が 3 秒以内に返るか）・SRAM の動く語数・FIFO・`+0x180` を見た:

| 書いたもの | 読み返し | 裏 CPU | 動く語 | FIFO |
|---|---|---|---|---|
| （書く前） | — | 応答あり | 497 | 映像 約 9,300 本/秒 |
| `0x101113b0 ← 0a220000` | **`0a220000`（残る）** | 応答あり | 499 | 変わらず |
| 同 `← 00020000`（戻し） | `00020000` | 応答あり | — | — |
| `0x10111058 ← 3` | **`0000000b`（残らない）** | 応答あり | 498 | 変わらず |

- `0x101113b0` の 3 ビットは書けるが、**裏 CPU にも TS 入力にも効かない**（別のブロックの
  リセットか、起動時にしか見られないもの）【推定】。
- `0x10111058` の bit 3 は、一度立つとメイン CPU からは落とせない（ただし上の訂正のとおり、
  裏 CPU の起動とは関係が確認できていない）。

**∴ 裏 CPU を起こすリセット解除（`+0x180`）はメイン CPU からは戻せない一方向のもの**で、
メイン CPU から裏 CPU を止め直す口は、BHIF にもこのページにも見つからない。

### 5.6 自前 FW への含意

- **起動（1 回目）で csd 自身がしている書き込みは少ない**（§5.1・受信スタック仕様 §79）。
  csd を使わない起動は**未検証**で、進め方はユーザの判断待ち（2026-09-28）。
- **2 回目以降の入れ替えは、FW が協力する形にする**: メイン CPU からは止め直せないので、
  自前 FW に「新しいイメージを読み込んで起動ベクタへ飛ぶ」受け口（§7 の空き合図 bit 16/18 など）を
  持たせる。§5.2 のベンダの「やり直し」も、この形とみられる。
- **固まった FW は電源でしか戻らない**（ウォッチドッグや NMI（§8）での救済は未調査）。受け口を
  持つ小さな常駐部（ローダ）と、入れ替える本体を分けておけば、本体が割り込みを止めたり
  ローダを壊したりしない限りは電源なしで戻せる。
- **ハードの停止・ステップ実行が要るなら EJTAG**（§9）。

## 6. 割り込みの振り分け

- 裏 CPU が受ける割り込みは `SUB_INT0_EN_0..2`（と、あれば `SUB_INT1_EN`）で選ぶ。
  **割り込み源はメイン CPU と共通の 96 本**で、SoC の周辺（UART・I²C・タイマ・XDMA・GPIO…）
  のどれでも裏 CPU に回せる構造である【GPL・§2】。
- 周辺ブリッジ（PBRD）の UART・I²C の割り込みには、別にマスクがある。U-Boot は
  `PBRD_INTENABLE_MAIN`（`0x10100010`）と **`PBRD_INTENABLE_SUB`（`0x10100014`）**を名前で
  持つ【GPL】。kernel は MAIN 側に `0xc0`（FUART0/1）を書く。
- 実測した裏 CPU の許可:

| 状態 | `SUB_INT_EN_0` | `SUB_INT_EN_1` | `SUB_INT_EN_2` | 出典 |
|---|---|---|---|---|
| 電源投入直後（csd 無し・裏 CPU は止まっている） | `0` | `0` | `0` | §5.1 |
| csd の load 直後（Initialise 前） | `00000080` | `0` | `0` | §5.1（csd が書く） |
| 段階 C リグ（blur 無し・Initialise 後） | `00000080` | `0` | `00000eee` | 本書 §3.2（FW が書く・§5.1） |
| ベンダ（配信中） | `000964a5` | `00000040` | `00003eee` | 受信スタック仕様 §41.1 |

  bit 7（源 7）は合図（§7）。**それ以外は、ベンダ FW が AV ハードのために受けている割り込み源**
  である。
- **状態レジスタ（`INT_ST`／`SUB_INT_ST`）はメイン CPU から読める**ので、AV ハードの割り込み線が
  いつ立つかを、裏 CPU の邪魔をせずに見られる（受信スタック仕様 §72.2 で源 7 について実証）。
  自前 FW を書く前に、どの源が何の出来事で立つかをこれで調べられる【推定・未実施】。

## 7. 合図（ソフトウェア割り込み）の空き

| 向き | レジスタ | 使える幅 | csd が使っているもの | 空き |
|---|---|---|---|---|
| メイン → 裏 | `+0x1b0`（許可 `+0x1b4 = 00070000`） | bit 16〜18 | **bit 17**（`0x00020000`・受信スタック仕様 §72.3） | **bit 16・18** |
| 裏 → メイン | `SW_INT`（`+0x1a0`）→ メイン CPU の SW IRQ 104〜135 | 32 本（`SW_INT_EN = ffffff07`） | 0〜2（API 応答・SPECIAL・FIFO）と 8〜31（`CSD_INTEVENT00`〜`23`） | **bit 3〜7**（登録なし） |

- 自前 FW では、csd と衝突しない**デバッグ専用の通路**（「ログが溜まった」「例外が起きた」
  「止まれ」）に空きビットを使える【推定・未検証】。
- ⚠ **`+0x1b4` に書くと AV が固まる**（受信スタック仕様 §67.4。電源で戻る）。
- ⚠ メイン CPU から `SW_INT` に書けるのは bit 0〜7 だけで、bit 0〜2 は即座に消費される
  （受信スタック仕様 §68.1）。裏 CPU がどう bit 8 以上を立てるかは未確認。

## 8. NMI

- 3 組とも `NMI_ST` と `NMI_EN` を持つ（§3）。裏 CPU の `NMI_EN`（`+0x134`）は `0`。
- **メイン CPU から裏 CPU へ NMI を送る経路があれば**、止まった自前 FW に割り込んで
  レジスタを DRAM に吐かせる「割り込み停止」に使える。**経路は未確認**で、優先度は低い。

## 付録 C. クロック／リセットのページ `0x10111000`〜`0x10111fff` の 0 でない語（2026-09-27）

csd の `NORMAL` の load の約 2 秒後（裏 CPU が走っている状態・Initialise と走行の後も同じ値）。
