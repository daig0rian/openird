Renesas EMMA3SEP 系機器が UPnP `X_UpdateFirmware(UpdateMode, FirmwareURL)` で受け取る
更新コンテナ（通称 factory.bin）の形式。OpenIRD の **factory 経路**（純正更新機構で初回
導入する image）が満たすべき対象であり、`openird-mkimage` の pack/unpack はこの仕様
だけを根拠に実装する。

- 機器側の実書き込み手順・mtd 対応・サイズ上限は
  [poe-br100-yb1-nand-update.md](poe-br100-yb1-nand-update.md)。
- 対象機は POE-BR100-YB1 (BMMPX1301) ほか emma3sep 系。**ヘッダ 0x14c のレイアウトは
  観察した全族で共通**、族タグ（§1）だけが異なる。

## 0. 鍵・パスワードの扱い（先に確認すること）

このコンテナは **AES 鍵**（§2）と **ZIP パスワード**（§3）の 2 つの秘密を要求する。

- **リポジトリ・配布物・ツールのいずれにも値を置かない。** 所有者が自分の機器から
  回収し、image 生成時に外部入力（引数／ファイル）として渡す。
- **回収手段も本リポジトリのスコープ外**（CONTRIBUTING.md §0）。本書は値も在処も書かない。
- GPL 側（u-boot 2010.09 / kernel 2.6.27.39）には復号ルーチンも鍵も存在しない
  ことを走査で確認済み（§6.9）。∴ 秘密は機器のユーザランド側にある。

## 1. 全体構造

```
factory.bin（外側コンテナ, <FAMILY>_UPDATE_v1b）
├─ 0x000..0x14b  ヘッダ 332B（平文・§2）
└─ 0x14c..EOF    暗号本体 = AES-128-ECB（§3）
                 └─ 復号 → 中間 ZIP（ZipCrypto 暗号化・§4）
                     ├─ <family>.zip … 無暗号 ZIP＝ペイロード本体（§5）
                     └─ csum         … <family>.zip の SHA-1（sha1sum -c 互換 1 行）
```

3 段（ECB → ZipCrypto → 無暗号 ZIP）。各段の完全性は独立に検算できる（§2 h38 / §4 csum）。

## 2. 外側ヘッダ（先頭 0x14c = 332 バイト）

| off | size | 内容 | 確度 |
|---|---|---|---|
| `0x00` | 32B | ASCII 族タグ `<FAMILY>_UPDATE_v1b\0`（NUL 詰め）。族が異なるコンテナは適用されない（§2.1） | 確定 |
| `0x20` | 16B | `h20`。復号後（平文）の MD5 と推定。暗号本体の各レンジの MD5 とは全不一致 | 推定・未検証 |
| `0x30` | 4B | `h30`。平文の CRC32 ないしフラグと推定。暗号本体の CRC32 とは不一致 | 推定・未検証 |
| `0x34` | 4B | バージョン `MM mm pp 00`（生バイト。`02 01 11`=2.1.17, `03 02 38`=3.2.56） | 確定 |
| `0x38` | 20B | `h38` = **SHA-1(暗号本体 0x14c..EOF)**。転送完全性用で、**署名ではない**（鍵なしで検算可能） | 確定（29 本全数で検算一致。`openird-mkimage probe-factory` が再現する） |
| `0x4c`–`0x14b` | 256B | `0x00` パディング | 確定 |
| `0x14c`–EOF | 可変 | 暗号本体。長さ = ファイル長 − 0x14c、**常に 16B の倍数** | 確定 |

### 2.1 族タグと機種の対応

| 族タグ | 実サンプルのある機種 | サイズ帯 |
|---|---|---|
| `BLUR` | POE-BR100-YB1 (BMMPX1301) | 16.6MB |
| `BR100-YB5` | POE-BR100-YB5 / XIT-AIR50 / AIR110W / AIR120CW | 50–63MB |
| `BR310L` | retail PIX-BR310 系（配信 dir `pix_br310w` / `pix_br310l`） | 16.5MB |
| `LINDBERG` | SB-TV06-WRIP (POE-BR310L-SB1) | 16.5MB |

- **族タグ = コンテナの族であって実モデル名ではない**（AIR110W/120CW も `BR100-YB5`）。
- 綴りは `LINDBERG`（`LINDBERGH` ではない）。**実コンテナ入手済み**（v1.0.2）。
  SB-TV06-WRIP の FW は retail 配信に存在せず純正アプリ同梱で配られるため、
  `pix_br310w` / `pix_br310l`（族 `BR310L`）とは別族である。
- **クロスフラッシュは多段で拒否される**（実証・§6.4）: 純正アプリのモデル白リスト →
  族タグ → モデル名照合 → 鍵/SHA-1 整合。他族コンテナは全 UpdateMode で flash されず、
  版数も不変（ブリックもしない）。∴ 自作コンテナは**実機が受理する族タグに一致**させる。
- **版数はゲートではない**（実機検証済）。純正イメージでダウングレードが受理されることを
  確認済み＝`0x34` の版数に順序制約は無い。自作コンテナ側も版数を上げる必要はない。

## 3. 暗号本体（0x14c 以降）— AES-128-ECB

- **AES-128 / ECB / パディング無し**。IV は不要（ECB）。本体長は常に 16B の倍数で、
  末尾に padding 記述子を持たない＝復号側は長さをそのまま使う。
- 復号結果は**そのまま標準 ZIP ファイル**（`PK\x03\x04` で始まる）。
- **鍵は族横断で単一**（確度: 確定）。根拠＝同一の 16B ブロック（＝ある定数の ECB 暗号文）が
  1 ファイル内で数百回反復し、その値が `BLUR` / `BR100-YB5` / `BR310L` / `LINDBERG` の
  **4 族・全 29 本で同一**。位置独立の反復は CBC/CTR では原理的に起きない＝ ECB の確定根拠でもある。
  - 含意: BMMPX1301 から回収した鍵は **SB-TV06-WRIP (BR310L) のコンテナにも通る**見込み。
- 鍵は純正アプリのマニフェスト鍵とは**別物**（§6.7/§6.8）。機器側にある。

## 4. 中間 ZIP — 伝統的 ZipCrypto（パスワード付き）

- AES-ECB 復号直後のバイト列がそのまま ZIP。**伝統的 PKWARE (ZipCrypto) 暗号化**
  （`unzip -P` 系の旧方式であり、AES-ZIP ではない）。
- エントリは正確に 2 つ:

  | 名前 | 内容 |
  |---|---|
  | `<family>.zip` | ペイロード本体（§5）。**無暗号 ZIP** |
  | `csum` | `<family>.zip` の SHA-1。`sha1sum -c` 互換の 1 行: `<40 桁 16 進>␠␠<family>.zip\n` |

- 機器側の更新スクリプトは `sha1sum -c csum` を通してから次段へ進む。∴ 自作時は
  **`csum` を再計算して整合させる**（ここを外すと展開前に止まる）。
- `<family>.zip` の名前は族に対応する（`BLUR` 族では `blur.zip`）。

## 5. ペイロード ZIP（無暗号）の中身

区画イメージ 5 点と、書き込みを駆動するシェルスクリプト。

| 名前 | 内容 |
|---|---|
| `vmlinux.img` | Kernel（uImage 形式・gzip） |
| `rootfs.img` | FileSystem（squashfs, root） |
| `app_bin.img` | App_binary（squashfs・純正アプリ） |
| `emma_fw.img` | EMMA_FW（squashfs・SoC FW） |
| `init_setting.img` | 初期設定 |
| `write.sh` | NAND 容量判定 → `write1Gb.sh` / `write512Mb.sh` の振り分け |
| `write1Gb.sh` / `write512Mb.sh` | 容量別の書き込み手順生成 |
| `delete.sh` | 更新完了後の後始末 |

- **各 `.img` は対応区画の先頭からの raw ダンプ**（追加ヘッダ無し）。
- **5 点とも任意**。スクリプトは各ファイルの存在を見てから書くため、**同梱しなかった区画は
  書き換えられない＝差分アップデートが成立する**。
- **書き込み先の mtd・サイズ上限・消去範囲は
  [poe-br100-yb1-nand-update.md](poe-br100-yb1-nand-update.md) §2**。上限超過分は黙って
  切り捨てられるため、pack 時に検証が要る。
- ブートローダ（mtd0）を書く枠はスクリプト側に存在するが、**実配布コンテナには同梱
  されない**＝通常経路では mtd0 は書き換わらない（同 §3）。

## 6. 自作コンテナの組み立て手順（openird-mkimage が満たす条件）

1. 区画イメージを用意する。**サイズ上限を厳守**（超過は切り捨て＝区画後半が破損する）。
2. 無暗号 ZIP `<family>.zip` にまとめる（`write.sh` 系スクリプトを同梱。純正コンテナから
   流用するのではなく、OpenIRD 側で仕様どおりに生成する）。
3. `<family>.zip` の SHA-1 を計算し `csum`（`sha1sum -c` 互換 1 行）を作る。
4. `<family>.zip` ＋ `csum` を **ZipCrypto** でパスワード ZIP 化（パスワードは外部入力）。
5. AES-128-ECB・パディング無しで暗号化（**16B 境界に合わせて事前に整える**）。鍵は外部入力。
6. ヘッダ 0x14c を組む:
   - `0x00` 族タグ（実機が受理する族と一致させる）
   - `0x34` バージョン
   - `0x38` = SHA-1(暗号本体)  ← **最後に計算**
   - `0x20`/`0x30` は §7 参照
   - `0x4c`–`0x14b` をゼロ埋め
7. 自前 HTTP サーバから配信し、UPnP `X_UpdateFirmware(download, URL)` で投入（§6.10–6.12 に
   再現手順あり。DNS 詐称も u-boot も不要）。

**OpenIRD の制約**: factory コンテナに含めてよいのは **kernel と rootfs に相当する区画のみ**。
vendor firmware / CAS / MAC 区画は温存する（全消し禁止）。
