# POE-BR100-YB1 の生 TS 経路 — 観察フェーズのまとめと実装への引き継ぎ

段階 C（chardev 契約＝生 TS が読める `/dev`）を満たす本線として、**裏 CPU の SRAM に
置かれる TS 入力 FIFO を、メイン CPU のカーネルで吸い出す**方式を育ててきた（2026-09-27 決定）。
**観察フェーズは 2026-09-28 に締めた。** 以後は、下の仕様だけを見てドライバを実装する段になる。

- 実装が見る仕様: [生 TS の取り出し](specs/poe-br100-yb1-ts-fifo.md)（FIFO・PID の列挙・ドレイナー・
  px4_drv 互換の ioctl への対応）、[AV のコマンド経路](specs/poe-br100-yb1-av-command.md)
  （ベンダの `.ko` 無しでデマルチプレクサを組む）、[MBIN ファーム容器](specs/mbin-firmware-container.md)
  （復調器の立ち上げと選局）。
- 観察の経緯と根拠: [受信スタック仕様](specs/poe-br100-yb1-reception-stack.md) §73〜§87。
  全体図は [信号経路の俯瞰](specs/poe-br100-yb1-signal-flow.md)。

> 限定受信（B-CAS / MULTI2 / ARIB スクランブル解除）は**永久に対象外**。この経路が
> 扱うのはスクランブルされたままのパケットで、OpenIRD はデスクランブラを開かない。

---

## 1. 到達点

**ベンダの AV 側のカーネルモジュールを「起動時の `csd.ko`」だけにした経路で、放送の TS を
参照受信機とビット単位で同じに取り出せる**（§87）。

```
[起動]  mtd5 の FW（emma3sep_driver_std_op0.mem）→ 物理 0x30000
        insmod csd.ko（裏 CPU を起こす）→ rmmod csd.ko（裏 CPU は走り続ける）
[選局]  MXL683 ← GPL の i2c だけ（MBIN は blur から実行時に取り出して転送）
        選局語 = 64 × (X + 1/7)、ロック = 0x1129 の下位 4 ビット かつ 0x112e == 1（1.4〜1.7 秒・§86.1）
[組む]  裏 CPU のコマンドスタック（共有メモリ 0x10000・合図 0x100001b0）に 6 種のコマンド
        Initialise / OpenDevice ×3 / 入力源 / フィルタ確保 / PID 設定 / 無効化
[吸う]  AV SRAM の TS 入力 FIFO（27 MHz の到着時刻＋188B・スクランブルされたまま）
        → hrtimer 100µs → 軽い FIFO は CPU、重い FIFO は XDMA でリングへ
        → 到着順の待ち行列 → read()
```

ベンダの `val_merge.ko`・フロントエンドのモジュール（`ei2c_ofdm_drv`・`io_controller_drv`・
`fe_*`）・`mem2`・Dione（`h57fmb`）はどれも要らない（§82）。

## 4. 実装の課題（優先順）

1. **chardev ドライバ（`ird-tuner-yb1` 相当）**: 起動（FW の書き込み・csd の load と unload）、
   MXL683 の選局（カーネルの I2C から）、コマンド経路、ドレイナー、px4_drv 互換の ioctl
   （ts-fifo 仕様 §11）を 1 つにまとめる。**PID の列挙の自動化**を含む: 選局 → 固定 PID の
   フィルタ → 流れてくる PAT/PMT/CAT を読んで列挙 → 2 機器（36 本ずつ）に振り分けて付け替え →
   版の変化に追従。recpt1/recisdb から録れることが段階 C 完了の判定。
2. **ドレイナーの頑健化**:
   - 忙しい時間帯（起動直後のログの吸い出し・`gzip` など）に 1 本欠けることがある（§76.3・§82）。
     DMA が遅れた周期でも到着時刻の走査を続け、遅れが大きければ CPU コピーに切り替える。
     （遅れた転送を最大 40µs 待つ形は入れた・下。忙しい時間帯での効き目は未確認。）
   - **速い多重で欠ける**（2026-10-15・受信スタック仕様 §86.1）: 19〜20.6 Mbit/s の ch 13・60 で、
     15 秒に 25 本前後（毎秒 1.7 本ほど）。どれも `torn`（写している間にスロットが上書きされた）で、
     化けは 0。16.5 Mbit/s の ch 27 では 0。→ **原因が分かり、直した（2026-10-16・SB-TV06-WRIP で
     確認）**: 取るスロットが最後と最初にまたがると転送が FIFO 全体（約 100µs）になり、次の周期に
     まだ続いていてその周期を休んでいた。長い範囲を 2 回に分け、続いている転送は最大 40µs 待つ
     （ts-fifo 仕様 §7.4・§7.6）。WRIP の ch 13・27・60 で計 224 万本・途切れ 0、CPU は変わらず。
     **YB1 の実機でも確かめた（2026-10-17）**: `v26.10-rc4-13-geb4be45` を `sysupgrade` で入れ、各 25 秒で
     ch 13 の連番の途切れが 10（前の版 `5318524`）→ 0。ch 27・60 も 0。T13・T60 もロックした。
     CPU（系全体・空回しの物差し）は ch 27 が 28.4% → 33.9%、ch 13 が 31.6% → 36.2% と 5 点ほど重い
     （SB-TV06-WRIP でも同じ傾向。周期の処理のソースは変えていない区間でも重くなった＝置き場所と
     推定・据え置き。WRIP の bring-up 仕様 §12.7）。
   - スロット数は設定で変わる（FIFO 2 が 7 か 8・§87.2）。ロード時の数え方の検査を強める。
   - **ヌルは運べない**: ヌルは 32µs 間隔で長く続けて来て、7 スロットの FIFO は約 190µs で一巡する
     （§87.1）。運ぶなら周期を詰めるか、ヌルだけ別の扱い（数えて作り直す等）にする。当面は
     ヌル抜きの TS を出す。
3. **OpenIRD 自身のカーネル・rootfs に載せる**: ここまでの試験はすべてベンダのカーネル
   （2.6.27.39）の上。YB1 の OpenIRD イメージ（GPL カーネルの再ビルド・rootfs を squashfs 3.1BE で・
   `pack-factory`）は段階 A 側の残件で、その上でドレイナーとコマンド経路を動かす。
4. **CPU**（系全体 約 31%）: 最新の 1 本を 1 周期待たずに済めば周期を延ばせる、SRAM に単調に
   増える到着の計数があれば走査を 1 語にできる（どちらも観察が先・§78.6）。

## 5. まだ分かっていないこと（急がない）

- 受かる 10 局それぞれの PID の数（フィルタ 72 本で足りるか。557 MHz は告知分を含めて 50 本）。
  機器 1（FIFO 1）が使えれば 108 本になる（未検証）。
- C/N の ±1 dB より良い換算（広い範囲の較正）。ch 25 のロックの時間。
- データリングの折り返し位置、エントリ 0 の出し方、フィルタの解放の呼び出し。
- recpt1 系・Mirakurun がヌル抜きの TS で困らないか。
- **裏 CPU を csd 無しで起こすこと**: 打ち切り（§79・§80。調べが安全判定で止まり、ユーザの判断で
  避けた）。起動は所有者の機器上の `csd.ko` に任せる。

## 6. 検証の道具と運用

- **参照受信機**: 別ホスト（192.168.11.33）の PX-M1UR。`/dev/pxm1urvideo1` は Mirakurun の #2 と
  共用で、**使うときはユーザ（とそのホストの担当セッション）に空けてもらう**。空きの確認は
  `pgrep -a recisdb | grep "device /dev/pxm1urvideo1"`（`pgrep -f` は確かめる ssh のシェル自身に
  当たる）。取り込みは `--no-decode`・カードリーダは使わない・照合の後に TS を消す。
- 照合: `tools/host/tsref.py`（どちらのホストでも TS を `pid cc crc32` のハッシュ列にする。
  参照側、YB1 側＝recpt1 で録った TS のどちらにも使える）・`tools/host/tshashcmp.py`（2 本を
  突き合わせて bit-exact/欠落/誤りを出す）。観察期は YB1 側を `yb1-mem @file 0 <len> hashes`
  で出していた（同じ CRC 形式）。中身はどちらのホストからも出さず、パケットごとの CRC-32 だけを運ぶ。
- 実機: `tools/yb1-fifodrain`（ドレイナー・`avwatch`）、`tools/yb1-cmd`（コマンドを積む・
  `next`/`auto` で続きから）、`tools/yb1-ioctl` の `trace`（ベンダの呼び出しをコマンドとして記録）、
  `tools/host/trace2cmd.py`、`yb1-mem`（`fifo`・`burn`・`locate`）、`yb1-mxl`。
  リグのフックは `tools/vendor-rootfs/openird-pre-stagec.sh`（1 回きりのフラグ
  `openird-nocsd-once`・`openird-min-once`）。運用は [リグの手順](poe-br100-yb1-rig.md)。

## 7. 退避路

この方式が行き詰まった場合の候補（いずれも CLAUDE.md の課題として残す）:

- **裏 CPU の FW の書き換え**（FIFO から DRAM へ全部運ばせる）。§1-1（ベンダバイナリを
  配布しない）・§1-3（逆アセは別セッション）との整合を先に詰める必要がある。
- **ハードウェアタップ**（復調器 MXL683 と SoC の間の TS 線）。

（この退避路は使わずに済んだ。§8 のとおり本線で段階 C の受け入れを通した。）

## 8. 受け入れ検証（段階 C 完了の実証・2026-10-10）

§4.1 のとおり段階 C の完了判定は「**未改造の recpt1/recisdb がこの chardev から録れること**」。
本線（ird-tuner-yb1 を OpenIRD カーネルに載せたイメージ＋OpenIRD rootfs）で、これを実機で通した。

- **recpt1 クロスビルド**: `tools/host/build-recpt1.sh`（stz2012 版を pin した commit で取得し、
  機種の Buildroot musl toolchain で **MIPS BE 静的**にビルド。libarib25 は入れない）。recpt1 の
  ABI（`driver/pt1_ioctl.h`）はドライバの px4_drv 互換 ioctl と一致（`SET_CHANNEL _IOW(0x8D,…)`/
  `START_REC`/`STOP_REC`/`GET_SIGNAL_STRENGTH`）＝スクリプトが機械で確かめる。配布物には含めない
  （所有者が自機の検証に使う道具）。
- **録れること**: 実機（NAND の OpenIRD カーネル＋OpenIRD rootfs）で
  `recpt1 --device /dev/irdvideo0 <ch> <sec> <file>` が成立。ch27 で 10 秒＝103,786 パケット・
  **連続性エラー 0・transport_error 0・同期不良 0**（188B 整列・先頭から 0x47）・C/N 29.2 dB。
  起動は `/etc/init.d/S30tuner`（所有者機の mtd から FW を物理 `0x30000` に `dd` → csd.ko を
  load/unload → `blur` の MXL MBIN を `ird-mbin` で取り出して driver の `firmware` に流す → `start`）。
- **ブリッジ（TS サーバ/クライアント）**: `recpt1 --http <port> --device /dev/irdvideo0` で YB1 が
  TS サーバ（daemon）になる。クライアントは `GET /<ch>[/<sid>]` で生 TS を octet-stream で受ける
  （別ホストから ch27 取得を確認）。自作デーモンは要らず、両端が本物 recpt1。**ポートは引数必須**
  （`--http` は省略できる既定ポートを持たない。recpt1 内蔵の定数は 12345）。EPGStation 既定の 8888 や
  Mirakurun の 40772 と紛れないポートを選ぶ（例: 12345）。
- **参照受信機とビット一致（再確認）**: 別ホスト .33 の PX-M1UR（recisdb 1.2.4・`--no-decode`
  `--no-strip`）と YB1 で同じ地上波（ch24）を同時録画し、`tsref.py`→`tshashcmp.py` で突合。
  重なった区間で、スクランブル済みの映像 PID `0x0111` が **device 先頭から 27,285 パケット連続で
  bit-exact（missing 0）**、音声/データ `0x1003`/`0x1004`/`0x0181` も同様に連続一致。高エントロピーの
  スクランブル列が連続一致する＝ドライバが放送 TS をバイトのまま出していることの実証（§87 の
  観察期の一致を、出荷するドライバ＋本物 recpt1 で裏取り）。参照機は Mirakurun #2 と共用のため、
  ホストの担当セッションに依頼して Mirakurun から外してもらい、使用後すぐ返した。TS 実体は双方の
  ホストから出さず、照合後に消した。
- **残件**: 録画窓を広く重ねた照合（今回は窓の重なりが小さく、重なり内は完全一致だが母数が小さい）、
  ヌル抜き TS での上位（recpt1 系・Mirakurun）の相性、ドレイナーの頑健化（§4.2）。
