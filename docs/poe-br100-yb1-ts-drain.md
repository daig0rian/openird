# POE-BR100-YB1 の生 TS 経路 — SRAM FIFO ドレイン方式の現在地と課題

段階 C（chardev 契約＝生 TS が読める `/dev`）を満たす本線として、**裏 CPU の SRAM に
置かれる TS 入力 FIFO を、メイン CPU のカーネルで吸い出す**方式を育てる（2026-09-27 決定）。
この文書はその**方針と課題の地図**。実装が見る仕様は
[生 TS の取り出し](specs/poe-br100-yb1-ts-fifo.md)、観察の経緯と根拠は
[受信スタック仕様](specs/poe-br100-yb1-reception-stack.md) の §73〜§78、全体図は
[信号経路の俯瞰](specs/poe-br100-yb1-signal-flow.md) にある。

> 限定受信（B-CAS / MULTI2 / ARIB スクランブル解除）は**永久に対象外**。この方式が
> 扱うのはスクランブルされたままのパケットで、OpenIRD はデスクランブラを開かない。

---

## 1. 仕組み（いま動いているもの）

```
MXL683 ─TS→ [TS 入力＋PID 選別]  ── 表に載った PID の 188B だけ、スクランブルされたまま
                 │
                 ▼
         AV データ SRAM 0x10030000〜 （メイン CPU から読める）
           FIFO ×3：220B スロット 7/6/8 個（到着時刻 27MHz＋188B）。1 機器＝1 FIFO＝PID 36 個
                 │                          └→ 裏 CPU の FW が PES/セクションに組み立てる（従来の経路）
                 │ hrtimer 100µs ごとに全スロットの到着時刻を読み、時刻順に:
                 │   軽い FIFO は CPU でリングへ（転送を起こす前に済ませる）
                 │   重い FIFO は XDMA チャネル 2 でリングへ直接（アドレス順）
                 ▼
         DRAM のリング（220B の要素 ×4,750＋予備 16）＋ 到着順の待ち行列（要素の番号）
                 │ read() で 188B を取り出す
                 ▼
         /dev/yb1fifo  →  ユーザランド
```

- 部品: `tools/yb1-fifodrain/fifodrain.ko`（ドレイナー）、PID の設定は今のところ
  ベンダ `val_merge.ko` の ioctl（PID フィルタ＝種別 7 を「確保・PID・有効化」の 3 手で張る。§77.1）。
- **★ 多重の全体（§77）**: 規則どおりに列挙した PID を 2 機器に分けて載せ（機器 2 に重い 31 個＋PAT、
  機器 1 に軽い 18 個）、**ヌル以外 110,911 本を 1 本も欠かさず、参照受信機とビット単位で一致**
  （35 PID すべて本数比 1.000、欠け 0・化け 0）。
- **CPU（§78）**: 系全体（読み手 `cat` 込み）で **40.4% → 30.8%**、コールバックは 25.6% → 13.2%
  （ヌル以外 毎秒約 10,900 本）。作りを変えた後も参照受信機とビット単位で一致。
- 実証（§74/§75）: 映像 PID 1 本（13.75 Mbps・毎秒約 9,100 本）で、**30 秒・28 万本を
  取りこぼし 0**。`/dev` から読んだファイルも同期の乱れ 0・連番の途切れ 0。
  コールバックの CPU は **5.4%**（1 パケット約 2.8µs、1 周期の固定費約 2.9µs）。
- **正解データとの照合（§76）**: 別ホストの PC 用チューナ（PX-M1UR・recisdb・デコード
  なし）で同じ局を同時に取り込み、パケットごとの CRC-32 で突き合わせた。YB1 の映像 PID
  **91,659 本がすべてビット単位で一致**し、取りこぼし・化けとも 0。

## 2. 確定していること

| 事実 | 根拠 |
|---|---|
| SRAM 64KB（`0x10030000`〜`0x1003ffff`）はメイン CPU から mmap／ioremap で読める。`0x10000000`〜`0x100fffff` は読んでも固まらない | §73.2 |
| TS 入力 FIFO は 3 本、スロットは 220B で FIFO 0/1/2 が 7/6/8 個。到着時刻（27.000 MHz）＋ヘッダ込みの 188B。埋まる順番はアドレス順ではない（待ち行列は空きスロットの列） | §73.6/§77.3 |
| FIFO に入るのは PID 表（`0x1003066c`・16bit×108 項）に載せた PID だけ。全 PID 素通し（`nr=0x48 {機器,0}`）でも増えない | §73.6 |
| 映像 PID を載せると **scrambling_control 2/3 のまま**入る（平文 0） | §73.9 |
| PID 表の bit15（有効）を落としても FIFO への流入は止まらない＝門は別にある | §73.9 |
| パケットの到着間隔は 32.0µs 単位で、最小 32.0µs。32µs 間隔の連続は最長 2 回 | §75.3 |
| SRAM の読み出しは 1 語 0.23µs・上限約 17 MB/s。キャッシュ経由でも同じ | §75.1 |
| XDMA は `MEM_LIST3 = 0x38000000`（bit 27＝転送先が DRAM）で SRAM→DRAM を運べる。完了は `MEM_LIST2 == 0`。チャネル 2 は段階 C で未使用 | §75.2 |
| ドレイナーは 100µs で定常の取りこぼし 0。150µs ではまれに欠ける。400µs では CPU コピーでも欠ける | §74.2/§75.4 |
| 557 MHz の多重は **毎秒 11,496 本（17.29 Mbps）・PID 36 個**（ヌル以外 35 個）。ヌルは 4.0% | §76.1 |
| YB1 の生 TS は参照受信機の TS とビット単位で一致（映像 91,659 本） | §76.2 |
| FIFO に入れるには種別 7 を「確保・PID・有効化」の 3 手で足りる（リング不要） | §77.1 |
| フィルタは 1 機器 36 個（PID 表 108 項の 3 等分）。機器 1 → FIFO 0、機器 2 → FIFO 2 | §77.2 |
| スロット数は FIFO 0 が 7、1 が 6、2 が 8。待ち行列は空きスロットの列で、PID が多いと埋まる順番はアドレス順でない | §77.3 |
| 全 PID を載せて、ヌル以外 110,911 本が参照と 100% 一致（35 PID） | §77.5 |

## 3. 前提と、壊れやすいところ

- **FIFO の形は、この FW 版で実機から読んだもの。** 制御ブロック `0xec00`、220B のスロット、
  PID 表の位置は、裏 CPU の FW（mtd5 の `emma3sep_driver_std_op0.mem`）の配置に依存する。
  ドレイナーは待ち行列からスロットを毎回読み直すが、形が変われば追従しない。
  ロード時に「パケット長 `0xbc`」「スロット間隔 220」などを検査して、合わなければ拒否すべき。
- **余裕は時間で決まる。** スロットの再利用は最短で「スロット数 − 1」本後（FIFO 2 なら 7 本×32µs＝224µs）。
  周期 100µs、「最新の 1 本は 1 周期待つ」、DMA の回収は次の周期、の積み上げで間に合っている。
  流量が上がる（多くの PID を載せる）と、再利用が早まって余裕が減る。
- **割り込みを長く止めるものに弱い。** リグの `dmesg -c` ループでタイマの遅れが出た。
  製品のカーネルでは、`CONFIG_PREEMPT` 下で長い割り込み禁止区間が無いことを確かめたい。
- **メモリが混むと DMA が遅れ、その周期を丸ごと飛ばして取り残す**（§76.3。YB1 上で
  `gzip -9` を走らせた時間帯に 5 回・38 本欠けた）。転送が終わっていなくても到着時刻の
  走査は続け、遅れが大きいときは CPU コピーに切り替えるなどの手当てが要る。
- **XDMA チャネルの共有。** NAND ドライバがチャネル 0 を使い、`LIST_ENABLE` を
  読み書きせずに自分のビットだけ書く。「書いた 1 の bit だけ効く」前提で共存している
  （ベンダ製品でもチャネル 0 と 1 が並走していたので、その前提は妥当と見ている。未検証）。
- **PID の設定は、まだベンダの `.ko` 経由。** 段階 C のクリーン化には、§72 の手順
  （コマンドスタック＋合図）で自分で積む必要がある。

## 4. 課題

### 4.1 PID の列挙（網羅）— いちばん大きい

FIFO には**PID 表に載せた PID しか入らない**。表は 108 項で、8192 の全 PID は載らない。
∴ この方式で出せるのは「**多重に存在する PID を列挙して、全部を表に載せた**」TS である。

- **列挙の規則は規格だけで閉じる（§76.1/§76.4）。** ARIB TR-B14（英訳 v6.7-E1。英訳版は
  全分冊が公開されている）に従って:
  1. **固定 PID**（Vol.4 Table 5-4）: `0x0000` PAT、`0x0001` CAT、`0x0010` NIT、`0x0011` SDT、
     `0x0012`/`0x0026`/`0x0027` EIT、`0x0014` TOT、`0x0023`/`0x0028` SDTT、`0x0024` BIT、
     `0x0029` CDT の 12 個。まれにしか送られない表（SDTT・CDT）もあるので、実在を待たずに載せる。
  2. **PAT** → NIT と各番組の PMT。
  3. **PMT** → PCR、各 ES、番組ループと ES ループの **CA 記述子（`0x09`）とアクセス制御記述子
     （`0xF6`）** が指す ECM の PID。
  4. **CAT** → 同じ 2 種の記述子が指す EMM の PID。
- **実測で裏が取れた。** 557 MHz のヌル以外の 35 PID は、この規則ですべて揃う。当初
  「どこからも辿れない」とした `0x0900`（EMM）と `0x0902`（ECM）は、アクセス制御記述子
  （`0xF6`）で告知されていた（解析が `0x09` しか読んでいなかった）。PID 表の走査で実在を
  探す必要は、少なくともこの局では無い。
- 告知されていても流れていない PID（番組 `0xfff0` の 11 本）もあり、規則どおりに載せると
  50 個前後。**108 項に収まる。** 落ちるのはヌル（4.0%）だけ＝出力は**ヌル抜きの TS**。
  recpt1 系・下流の録画ツールがそれで困らないかを確かめる。
- **CA 関係の PID（ECM/EMM）も生 TS の一部として運ぶ。** 下流で所有者のカードを使う道具が
  必要とする。OpenIRD はパケットを運ぶだけで、中身は解釈しない。
- **動的に変わる。** 番組構成が変わると PMT が変わる（版番号が上がる）。実際に、15 秒
  あけた取り込みで副音声 `0x0111` が PMT から消えていた。選局し直すと PID の集合が丸ごと
  変わる。PAT/PMT/CAT の版を見張って、表を追従させる仕組みが要る。
- **誰が列挙するか。** px4_drv 互換の chardev は「選局したら TS が全部出てくる」契約なので、
  列挙はドライバ側（カーネル、または対になる小さなデーモン）が自動で行うのが筋。
  PAT/PMT の解析自体は小さい。
- **108 項の配分。** 機器 1 はフィルタ `0x22`/`0x23`、機器 2 は `0x6a`/`0x6b` を使っていた。
  機器ごとに何項使えるか、1 つの FIFO に何 PID まで入れられるかは未測定。
- **フィルタの種類とコスト。** いまは PID ごとに「ペイロードフィルタ（種別 6）＋リング」を
  張っていて、裏 CPU の FW がその PID の PES を組み立てて DRAM に書いている。FIFO に
  入れるだけなら不要な仕事で、裏 CPU とバスの負荷になる。**FIFO に入れる最小の設定**
  （種別 7 だけで足りるか、リング無しで通るか）を探す。
- **「全部通す」門の可能性。** bit15 は門ではなかった（§73.9）。FIFO 制御ブロックの
  `+0x38 = 0x471fff00` と `+0x3c = 0xff1fff00` は「sync＋PID の値とマスク」の形をしている。
  ここが門なら、マスクで全 PID を通せるかもしれない。ただし**裏 CPU の FW の変数を書く**
  実験になるので、やるなら別途判断する。

### 4.2 多重全体での負荷と FIFO の容量

- 多重の全 PID を載せると、流量は映像 1 本（毎秒約 9,100 本）より大きい。
  **参照受信機の実測で毎秒 11,496 本（ヌル込み。ヌル以外は約 11,030 本）**（§76.1）。
- **実測（§77）**: ② 余裕は足りた（周期 100µs で連番の途切れ 0）。③ 裏 CPU も全 PID を
  さばいた（参照とビット一致・網羅 100%）。**① CPU は換算の約 6% に対し実測 21.4%**。
- **CPU の行き先を測って直した（§78）**: SRAM の口の取り合いは実在（XDMA の転送中は CPU の
  SRAM 読みが 1 語 0.3µs → 1.76µs）、作業領域からの写しが DRAM の取り損ねで 1 本 4.7µs。
  CPU 側の FIFO を先に済ませ、XDMA にリングへ直接書かせて到着順は待ち行列で渡す形にして、
  系全体 40.4% → 30.8%。残りはコールバック 13%・タイマ割り込みの出入り 6%（1 回約 6µs）・
  読み手 5〜6%。
- FIFO は機器ごとに 1 本（機器 1 → FIFO 0、機器 2 → FIFO 2）。2 本使うので、同じ PID を
  両方に載せない（重複する）。出力の PID 間の並びは、XDMA 側が 1 周期遅れるぶんだけ前後する
  （同じ PID の中は到着順）。

### 4.3 読み出しの最適化

- 読み手（`cat`・4KB 読み）は系全体で 5〜6 点（§78.4）。うち `read()` の中が 1 本 3.4µs
  （DMA の後の DRAM の読み）。先読み・大きい読み・起こす間隔（256 本）は効かなかった。
  §75.5 の「5〜17%」は `/proc/stat` の標本化の誤差だった（§78.1）。
- 残る候補: リングを `mmap` で見せる（コピー無し。ただし px4_drv 互換の契約は `read()`）。
- 到着時刻（27MHz）を持っているので、192B の TTS 形式で出す選択肢も作れる。

### 4.4 デマルチプレクサ制御のクリーン化

- いまの PID の設定は、ベンダ `val_merge.ko` の ioctl を使っている（＝段階 B の依存が残る）。
- §72 でコマンドの積み方と合図は割れている。ドレイナーと同じモジュールか対になる
  モジュールから、Initialise → OpenDevice → 入力源 → フィルタ確保 → PID → 有効化を
  自分で積めば、ベンダの `.ko` を 1 つも使わずに済む。
- 裏 CPU の FW（mtd5）は所有者の機器上のものを実行時にロードする（§1-5 と同じ扱い。配布しない）。

### 4.5 chardev 契約（px4_drv 互換）

- 選局（MXL683・I2C。いまはユーザランドの `tools/yb1-mxl`）、PID の列挙（4.1）、
  ドレイン、`/dev` を 1 つのドライバ（`ird-tuner-yb1` 相当）にまとめ、px4_drv と同じ
  ioctl（選局・ストリーム開始／停止など）で叩けるようにする。
- recpt1/recisdb から実際に録れることが、段階 C 完了の判定になる。

### 4.6 頑健性と横展開

- ロード時の形の検査（3 の 1 項目め）、順番の食い違い（`resync`）や DMA の遅れ
  （`still_running`）の監視を、製品でも残す。
- 選局し直し・電源断・FW 再ロードをまたいだ振る舞い。
- **SB-TV06-WRIP** は AV スタックが同じ（関数表 76 本一致）。同じ SRAM・FIFO・XDMA が
  使えるかを確かめれば、横展開は安い。

## 5. 次の一手（提案順）

1. ~~全 PID を手で載せて測る~~ → **済（§77）**。網羅 100%・ビット一致。
   ~~FIFO に入れる最小のフィルタ設定~~ → **済（§77.1）**: 種別 7 を 3 手。
2. ~~全 PID 時の CPU を下げる~~ → **一段済（§78）**: 系全体 40.4% → 30.8%。さらに下げるなら
   (a) 最新の 1 本を 1 周期待たずに済むかを確かめて周期を延ばす（割り込みの出入り 6% と毎周期の
   走査が減る）、(b) SRAM に単調に増える到着の計数があるかを探し、何も来ていない周期の走査を
   1 語にする。どちらも観察が先。
3. **周期を飛ばさない作りにする**（3 の「メモリが混むと DMA が遅れる」への手当て）。
4. ~~読み出しの最適化~~ → 測った（§78.4）。`read()` の契約の中では下げる手が見つかっていない。
5. **デマルチプレクサ制御のクリーン化**（4.4）→ **chardev 化**（4.5）。PID の列挙と 2 機器への
   振り分けを、選局と PMT の版の変化に合わせて自動で行う（いまは手で作った ioctl の列）。

**検証の道具（常用）**: 別ホストの PC 用チューナで同じ局をデコードせずに取り込み、
PID の在庫・流量と、パケットごとの CRC-32 を YB1 と突き合わせる（§76。中身はどちらの
ホストからも出さない）。

## 6. 退避路

この方式が 4.1〜4.2 で行き詰まった場合の候補（いずれも CLAUDE.md の課題として残す）:

- **裏 CPU の FW の書き換え**（FIFO から DRAM へ全部運ばせる）。§1-1（ベンダバイナリを
  配布しない）・§1-3（逆アセは別セッション）との整合を先に詰める必要がある。
- **ハードウェアタップ**（復調器 MXL683 と SoC の間の TS 線）。
